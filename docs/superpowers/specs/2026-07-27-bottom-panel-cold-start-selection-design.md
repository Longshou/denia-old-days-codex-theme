# 底部终端冷启动选中样式性能修复

## 问题

底部面板第一次打开时，原生终端会先创建容器和标签页，再批量创建 xterm 字符行。主题开启后，
字符行为空的中间帧会停留约 190～216 毫秒，用户看到警告条或空终端短暂停顿后，提示符才出现。

## 诊断

CPU、帧时间线和 CSS 单规则消融给出一致结果：

- 完整主题的 xterm `createRow -> _measure` 约为 146～183 毫秒，最长帧间隔约为
  169～216 毫秒。
- 关闭全部主题 CSS 后，字符行测量约为 83 毫秒，最长帧间隔约为 97 毫秒。
- 停止主题运行时并保留纯原生 Codex 后，字符行测量约为 93 毫秒，最长帧间隔约为 108 毫秒。
- 只移除 `.denia-old-days-ds-extension ::selection` 后，字符行测量约为
  92～103 毫秒，最长帧间隔约为 109～134 毫秒。
- 只移除 `:focus-visible` 规则后，最长阻塞仍约为 216 毫秒。

因此，主题运行时的面板状态同步和原生内联动画不是本次停顿的主因。根因是全局后代
`::selection` 规则参与 xterm 大批字符节点的首次样式解析，把原生终端冷启动成本放大。

## 设计

删除 `.denia-old-days-ds-extension ::selection`。原生任务内容、输入框和终端统一回退到 Codex /
系统文本选中样式。此次不使用 `:not(.xterm *)` 等宽泛排除选择器，也不在面板开关时动态启停
样式，避免继续让全应用后代选择器参与匹配或引入观察器时序竞争。

同时把 `findNativeToggle()` 的筛选顺序从“先读取所有按钮几何，再判断标签”调整为“先判断标签，
只对匹配候选读取几何”。这一改动不改变按钮识别结果，只消除每次工作面同步时无关按钮的
布局读取。

## 验收

- 样式表不再包含 `.denia-old-days-ds-extension ::selection`。
- 原生按钮标签不匹配时，不进入 `visible()` 几何检测。
- 静态验证、完整项目检查、安装和实时验证通过。
- 连续三次冷启动中，xterm 字符行测量和最大帧间隔回到纯原生基线附近。
- 输入框识别、侧栏收起、置顶摘要和底部面板状态同步没有回退。

## 实施结果

安装推荐方案后连续三次冷启动结果如下：

| 轮次 | 样式重算 | xterm 字符行测量 | 最大帧间隔 | 提示符出现 | 复位 |
| --- | ---: | ---: | ---: | ---: | --- |
| 1 | 240.3ms | 125.7ms | 135.4ms | 236.9ms | closed |
| 2 | 213.2ms | 117.3ms | 129.0ms | 229.2ms | closed |
| 3 | 211.4ms | 112.3ms | 123.9ms | 216.4ms | closed |

修复前完整主题的最大帧间隔约为 193～216 毫秒，提示符出现约为 327～360 毫秒；此前测得
纯原生最大帧间隔约为 108 毫秒。修复后主题侧放大已基本消除，剩余长任务主要位于 xterm
`createRow -> _measure` 原生初始化路径。
